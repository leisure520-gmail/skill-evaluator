# 轨道二：体系架构评估

评估整个 Skill 体系的架构成熟度。13 个加权维度，0-10 分制，S 级（>= 9.0）为唯一达标等级。

> **前置条件**：轨道一（全量质量评估）全部达标后，方可执行本评估。如有文件评估 < 9.0，必须先修复。近 30 天内已做过轨道一且全部 >= 9.0 且无文件变更，可跳过。
> **增量评估**：评估范围由 `references/eval-state.md` 确定，轨道二需全量扫描但可引用轨道一的增量结果。

---

## 13 维度评估框架

### D1：模块化封装（权重 10%）

每个 Skill 独立、可测试、可组合，有标准化的 inputs/outputs/constraints 声明。

| # | 检查项 | 通过标准 |
|---|--------|---------|
| 1.1 | 每个 SKILL.md 有标准化元数据声明 | name/description/status/order/version 齐全 |
| 1.2 | 每个 SKILL.md 声明输入输出契约 | 明确声明需要什么、产出什么、有什么边界 |
| 1.3 | 技能间依赖关系显式声明 | 声明与其他 skill 的依赖/组合关系 |
| 1.4 | 占位符机制完整 | 零硬编码残留 |
| 1.5 | anti-patterns 独立且豁免机制正确 | 豁免声明存在 |
| 1.6 | 子文档 frontmatter 完整 | 所有子文档含 name/description/status/order/version |

评分：9-10 所有文件有完整元数据 + inputs/outputs/contracts + 依赖关系图 | 7-8 SKILL.md frontmatter 完整 + 占位符 + anti-patterns + 子文档 frontmatter 完整 | 5-6 SKILL.md frontmatter 完整但子文档缺失或部分缺失 | 3-4 部分 SKILL.md 缺 frontmatter | 1-2 无标准化封装

### D2：渐进式披露（权重 8%）

按需加载，三阶段（发现->激活->执行），避免上下文爆炸。

| # | 检查项 | 通过标准 |
|---|--------|---------|
| 2.1 | SKILL.md 路由表有 level 字段 | must/ref/planned 三级 |
| 2.2 | planned 状态强制跳过机制 | 零加载 planned 内容 |
| 2.3 | 有技能摘要层 | AI 可先读摘要判断是否深入 |
| 2.4 | 上下文预算管理 | must 级文档总 Token 在预算内 |
| 2.5 | INDEX.md 快速路由 | 根据任务类型可直接定位 |
| 2.6 | 子文档 level 与路由表一致 | 子文档 frontmatter 的 level 与 SKILL.md 路由表声明一致 |

评分：9-10 三阶段发现 + 上下文预算 + 摘要层 + 按需降级 + 子文档 level 一致 | 7-8 level 分级 + planned 跳过 + INDEX 路由 + 子文档 level 一致 | 5-6 有路由表但 must 级过多或子文档 level 不一致 | 3-4 全量加载或缺少路由分级 | 1-2 无按需加载机制

### D3：TDD 工作流（权重 15%）

测试先行，RED-GREEN-REFACTOR 循环嵌入 Skill 执行流程。

| # | 检查项 | 通过标准 |
|---|--------|---------|
| 3.1 | spec 模板包含测试用例定义章节 | 有 GIVEN/WHEN/THEN 或等效 |
| 3.2 | plan 模板要求第一个 Task 是编写测试 | Task 1 = 编写测试用例 |
| 3.3 | testing-convention 在需求阶段被引用 | spec 阶段加载 testing-convention |
| 3.4 | 验收标准包含测试覆盖率要求 | 有明确的覆盖率阈值 |
| 3.5 | 代码生成工作流嵌入 TDD 循环 | 生成顺序：测试->实现->验证->重构 |

评分：9-10 spec 阶段定义测试 + plan 第一步写测试 + TDD 循环强制执行 | 7-8 验收阶段有测试要求 + testing-convention 存在 | 5-6 测试只在 Post-Flight 出现 | 3-4 有 testing-convention 但未嵌入需求流程 | 1-2 无 TDD 机制

### D4：三文件模式（权重 7%）

plan.md + context.md + tasks.md 结构化管理。

| # | 检查项 | 通过标准 |
|---|--------|---------|
| 4.1 | spec 和 plan 分离 | spec 和 plan 在不同目录/文件 |

| 4.4 | 任务清单是原子化的 | 每个任务有明确的文件和改动说明 |
| 4.5 | 三文件可独立加载 | 上下文信息自包含 |

评分：9-10 三文件完全独立 + context 可单独加载 + 任务原子化 | 7-8 spec + plan 分离 + plan 内分区明确 | 5-6 spec + plan 分离但 plan 承担过多职责 | 3-4 只有单文件需求文档 | 1-2 无结构化文件管理

## 评估执行流程

```
1. 确认轨道一已全部达标
2. Phase 1：数据采集
   -> 扫描目录结构，递归发现所有 .md 文件
   -> 读取所有 SKILL.md frontmatter 和路由表
   -> 读取所有子文档的 frontmatter（name/description/status/order/level/version）
   -> 交叉比对：子文档 frontmatter vs SKILL.md 路由表的一致性
   -> 读取根目录文件（INDEX.md、CONVENTION.md、GOVERNANCE.md 等）
   -> 引用轨道一的全量评估结果
3. Phase 2：逐维度评分
   -> 按 D1-D13 逐项检查
   -> 每个维度输出：评分 + 证据 + 问题列表
   -> 标记 BLOCK 级问题（评分 <= 4）
4. Phase 3：综合分析
   -> 计算加权总分
   -> 识别最薄弱的 3 个维度
   -> 分析维度间关联影响
5. Phase 4：改进建议
   -> 每个 <= 7 分的维度输出改进建议
   -> BLOCK 级问题输出紧急改进计划
6. Phase 5：报告输出
   -> 保存到被评估体系外部
7. Phase 6：持久化与历史对比
   -> 将报告保存到 {评估结果根目录}/{体系名称}/track2_{YYYY-MM-DD_HHmmss}.md
   -> 若存在历史评估报告，输出趋势分析
```

## 结果持久化

评估完成后，自动将报告保存为 Markdown 文件：

- **保存路径**：`{评估结果根目录}/{体系名称}/track2_{YYYY-MM-DD_HHmmss}.md`
- **默认根目录**：`./eval-results/`（相对于当前工作目录）
- **路径不存在时**：自动创建目录
- **保存内容**：完整评估报告（维度评分 + 问题建议 + 改进路线图 + 历史趋势章节）
